# 2026-10-19 Talos バージョン更新

## 実施内容

- Talos の目標バージョンを v1.14.4 に設定。
- 全7ノードを v1.11.6、v1.12.12、v1.14.4 の順で更新した。Talos Factory schematic はリポジトリの `talos/schematics.yaml` から生成した。
- cp-03 の古い etcd 状態を解消するため、利用者の指示に基づき EPHEMERAL パーティションを消去して再参加させた。バックアップは取得していない。
- `talos:upgrade-schematic` に対象バージョン指定と、すでに目標バージョンのノードをスキップする処理を追加した。
- devcontainer に `yq` を追加し、`talosctl` を Talos v1.14.4 に合わせた。

## 確認結果

- cp-01〜03、wk-01〜04 はすべて Talos v1.14.4。
- etcd は control plane 3台で構成され、全メンバーが voter (`LEARNER=false`)。
- Kubernetes Node 7台すべて Ready。実クラスタの Kubernetes バージョンは v1.32.0。
- cp-01 で `iscsi-tools` v0.2.0 と `util-linux-tools` 2.42.2 を確認した。
- バージョン更新前後に etcd、control plane Pod、CoreDNS、全ノード Ready の health check を実施した。
- `talconfig.yaml` の Kubernetes 目標は v1.34.1 だが、今回 Kubernetes の更新は行っておらず、実クラスタは v1.32.0 のまま。

## 互換性調査

- Talos v1.14 は v1.12.0 以降から更新でき、Kubernetes v1.32.0 以降に対応する。
- Talos v1.11 は v1.9.0 以降から更新できるため、今回の中間バージョンを v1.11.6、v1.12.12 とした。
- 参照: [Talos v1.14 compatibility](https://pkg.go.dev/github.com/siderolabs/talos/pkg/machinery/compatibility/talos114)、[Talos v1.11 compatibility](https://pkg.go.dev/github.com/siderolabs/talos/pkg/machinery/compatibility/talos111)、[Talos v1.14.4 release](https://github.com/siderolabs/talos/releases/tag/v1.14.4)

## Kubernetes ストレージ現状確認

- 実クラスタに Longhorn CSI (`driver.longhorn.io`) と DirectPV CSI (`directpv-min-io`) が登録されている。
- PVC、PV、Longhorn Volume、DirectPV Drive/Volume は存在しない。MinIO Tenant CR はあるが、root credentials の ExternalSecret が 1Password の参照先を解決できず未同期で、Tenant のデータ Pod/PVC は作られていない。
- Flux `platform-config` はこの ExternalSecret の health check で失敗し、`apps` は依存関係により未適用。
- Longhorn HelmRelease は v1.12.0 の pre-upgrade hook が `BackoffLimitExceeded` で失敗し、Helm remediation も `MissingRollbackTarget`。Longhorn の node disk は Ready と報告されるが、容量は各約 31 GiB。
- Talos の wk-01 を読み取り確認したところ、`/var/mnt/persistent-volume` は dedicated disk に mount されず `/var` は system disk (`sda`) 上にある。worker には scsi1/scsi2 相当の 275 GB disk (`sdb`/`sdc`) がある。Longhorn は現状、意図した専用 PV disk を使っていない。
- よってアプリ向け PVC が利用可能とはまだ確認できない。MinIO は Tenant 定義までで実利用されておらず、移行対象の PVC/PV データは見つからなかった。
- SeaweedFS の役割、DirectPV 用 disk の初期化、レプリケーション方式は未決定のため変更・初期化を行わず、利用者判断待ちとする。

## Longhorn / MinIO の移行作業

- 利用者の指示に基づき MinIO と DirectPV の GitOps 定義を削除し、Longhorn のみを汎用 PersistentVolume 向けに残した。実クラスタでは PVC/PV/Longhorn Volume/replica/BackingImage が 0 件。
- devcontainer を再構築し、Talhelper を 3.1.17 に更新。Talos v1.14 形式で CNI none、control-plane の KubeProxyConfig 無効化、worker UserVolume を生成できることを確認した。
- Talos v1.14.4 では `UserVolumeConfig` による専用ディスクの XFS 初期化が必要。wk-01〜wk-04 の scsi1 (`*-pv-0`) を `/var/mnt/persistent-volume` に mount し、Longhorn data path を kubelet container に bind mount した。ユーザーがバックアップ不要と確認済みで、各 disk は未使用であることを確認してから実行した。
- Talos の全 worker で UserVolume は Ready、各 `/dev/sdc1` は約 275 GB の XFS。Kubernetes Node は全台 Ready。
- Longhorn node の既存 disk UUID が新規 UserVolume と一致しなかったため、Longhorn disks を scheduling 無効化・replica がないことを確認してから削除し、同じ data path で再登録した。全4 disk が Ready、各約 269 GB の空き容量を認識している。予約容量は Longhorn 既定の 30% に設定。
- Flux HelmRelease は pre-upgrade Job の BackoffLimitExceeded と MissingRollbackTarget により Stalled だった。データを含む Longhorn Volume が 0 件であることを確認し、`upgrade.remediation.strategy: uninstall` を IaC と live HelmRelease に設定。Flux が Longhorn 1.12.0 の upgrade に成功し、HelmRelease Ready になった。hook を無効化せず、再 upgrade 時の pre-upgrade / post-upgrade checks は成功。
- wk-03 の engine-image DaemonSet Pod は probe が 4 秒で timeout し `Text file busy` が発生していた。Longhorn 1.12.0 で公式に追加された設定を使い、liveness probe timeout を 10 秒、failure threshold を 6 にした（period は既定の 5 秒）。HelmRelease は Ready、EngineImage は全 worker で deployed。
- 1 GiB の試験 PVC（replica 数 3）を作成し、Pod から書き込んだ marker が Pod 再作成後にも読み出せることを確認した。試験用 namespace、PVC/PV、Longhorn Volume/replicas、StorageClass はすべて削除した。
- `feat: configure Longhorn storage` を commit / push 後、Flux GitRepository と `platform-controllers`、`platform-config`、`apps` を revision `c51d30d` に reconcile した。全 Kustomization が Ready で、MinIO / DirectPV の namespace、Pod、CRD は cluster から削除された。
- Longhorn CSI (`driver.longhorn.io`) と `longhorn-rwo` StorageClass は利用可能。全 worker の EngineImage は deployed、engine-image Pod は全4台 Ready。PVC smoke test 成功後は試験用リソースを全削除し、cluster に PVC/PV/Longhorn Volume/replica は残っていない。
